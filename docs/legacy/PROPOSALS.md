# ۱) تب جدا برای سیگنال‌های لانگ و شورت

## نتیجه: پیشنهاد درستی است و توصیه می‌شود

دلیل فنی‌اش این است که **مدل داده از قبل دوطرفه ساخته شده** و فقط رابط کاربری یک‌طرفه مانده.
در `updateShortPlans()` (خط ۵۸۸) هر ارز از قبل هر دو پلن را کنار هم دارد:

```js
c.a.plans = {
  long : {side:'long', entry, stop, tp1, tp2, score:buyScore, gate},
  short: ShortEngine.plan(c, state.regime, shortOptions(c))
};
```

و این جداسازی در کل سامانه رعایت شده است:

| لایه | لانگ | شورت |
|---|---|---|
| موتور | `analyze()` + `buyPlan()` در `app.js` | `short-engine.js` (مستقل) |
| کارنامه | `perf.rec` با کلید `cb_perf_v1` | `shorts.records` با کلید `cb_short_v1` |
| نسخه‌ی استراتژی | `legacy-long-v1` | `short-pullback-v1` |
| خروجی CSV | `exportCSV()` | `exportShortCSV()` |
| دروازه | `evalCoinGate()` | شروط مستقل داخل `ShortEngine.plan` |

یعنی تب‌بندی **کشف یک ساختار موجود** است، نه تحمیل یک ساختار تازه. این بهترین نوع تغییر UI است.

## مشکلی که واقعاً حل می‌کند

الان صفحه ۹ بخش پشت‌سرهم در یک اسکرول عمودی است و بخش شورت (`#shortSec`) دقیقاً بین
«بهترین رمزارزها برای خرید» و «کارنامه عملکرد» گیر کرده است. حتی کامنت بالای آن در
`index.html` هنوز `<!-- Track record / backtest -->` است — یعنی بخش شورت بعداً و با عجله
در جای بخش دیگری درج شده. نتیجه برای کاربر:

- کاربری که دنبال خرید است، ناچار از میان فرصت‌های شورت رد می‌شود.
- کارنامه‌ی لانگ و کارنامه‌ی شورت دو جدول جدا با ظاهر متفاوت‌اند و کنار هم دیده نمی‌شوند.
- بخش شورت با `.short-card` و `.short-table` استایل کاملاً متفاوتی از بقیه‌ی داشبورد دارد
  (ساده‌تر و بدون کارت شیشه‌ای/گرادیان)، چون بعداً اضافه شده. تب‌بندی فرصت طبیعی‌ای است
  که ظاهر شورت را هم‌سطح بقیه‌ی داشبورد کنیم — که دقیقاً خواسته‌ی «گرافیک زیبا» است.

## طراحی پیشنهادی

سه ناحیه، نه دو تب خشک:

```
┌─ همیشه دیده می‌شود (مشترک) ──────────────────────────────┐
│  نمای کلی بازار • رژیم بازار • ترس و طمع • دروازه        │
│  ┌──────────────┬───────────────┬──────────────┐        │
│  │ 🟢 لانگ       │ 🔻 شورت        │ ⚖️ دوطرفه     │  ← tablist
│  └──────────────┴───────────────┴──────────────┘        │
└──────────────────────────────────────────────────────────┘
 تب لانگ   : بهترین خرید + نوار سیگنال‌های مجاز + کارنامه‌ی لانگ
 تب شورت   : فرصت‌های شورت + نوار مشابه + کارنامه‌ی شورت
 تب دوطرفه : مقایسه‌ی کنار هم — چند مجوز لانگ / چند مجوز شورت، و تعارض‌ها
```

ناحیه‌ی «مشترک» باید بیرون تب‌ها بماند، چون رژیم بازار و دروازه **ورودی هر دو موتور**اند
و پنهان‌کردنشان در یک تب، تصمیم را از زمینه‌اش جدا می‌کند.

تب سوم («دوطرفه») پیشنهاد اضافه‌ی من است و ارزان تمام می‌شود: منطق تعارض لانگ/شورت از قبل
در `shortConflict()` و `longCandidate()` (خطوط ۵۷۹–۵۸۵) نوشته شده ولی **هیچ‌جا به کاربر
نمایش داده نمی‌شود**. الان اگر شورت یک ارز به‌خاطر تعارض با لانگ رد شود، فقط یک جمله در
فهرست دلایل است. یک نمای دوطرفه این را به یک اطلاع مفید تبدیل می‌کند.

## نکات گرافیکی که با توکن‌های موجود جور است

`style.css` از قبل متغیرهای رنگی لازم را دارد و نیازی به پالت جدید نیست:

```css
--sbuy:#00e676  --buy:#4ade80   /* سبزهای لانگ */
--sell:#fb7185  --ssell:#ef4444 /* قرمزهای شورت */
```

پیشنهاد مشخص: یک متغیر `--side-accent` روی `<main>` تعریف شود که با تب عوض شود. چون
`.trade-strip`، `.tchip` و `.gatebox` از قبل با `var(--tc)` و `color-mix()` رنگ می‌گیرند،
کل داشبورد با تعویض تب به‌صورت خودکار هویت رنگی عوض می‌کند — بدون نوشتن CSS تکراری برای شورت.

## هشدارهای فنی که حتماً باید رعایت شوند

اینها را حین خواندن کد پیدا کردم و هرکدام می‌تواند یک تب‌بندی ساده را به باگ تبدیل کند:

**۱. موتور نباید به تب گره بخورد.** `shortCycle()`، `perfCycle()` و `detectEvents()` در
`afterCycle()` اجرا می‌شوند. اگر اینها را مشروط به تب فعال کنیم، معاملات فعالِ تب پنهان
دیگر ارزیابی نمی‌شوند و کارنامه بی‌صدا متوقف می‌شود. **فقط رندر باید تب‌آگاه شود، نه چرخه.**

**۲. تله‌ی `renderShorts()`.** خط اول این تابع (۶۴۶) کلید تازگی را ثبت می‌کند:

```js
function renderShorts(){
  state.shortFreshDisplayed = shortFreshKey();   // ← خط ۶۴۶
  const box=$('#shortPanel'); if(!box) return;
```

و `tick()` هر ثانیه آن را مقایسه می‌کند (خط ۱۳۱۰):

```js
if(state.shortFreshDisplayed!==shortFreshKey()){ updateShortPlans(); renderShorts(); refreshModal(); }
```

اگر برای بهینه‌سازی، در ابتدای `renderShorts()` یک `if(tab!=='short') return;` **قبل از**
خط ۶۴۶ بگذاریم، کلید هرگز به‌روز نمی‌شود و `tick()` هر ثانیه پلن ۱۰۰ ارز را از نو
می‌سازد. این یک نشت CPU خاموش است. هر `return` زودهنگام باید **بعد از** خط ۶۴۶ باشد.

**۳. DOM هر دو تب باید بماند.** `initShortUI()` (خط ۶۶۸) هندلرها را یک‌بار موقع بوت
به `#shortEnabled`، `#shortFilter` و `#shortCSV` می‌بندد. اگر تب‌ها DOM را حذف/بازسازی کنند،
این هندلرها از بین می‌روند. راه درست: `display:none` روی بخش‌ها (یا کلاس روی `<main>`)،
نه `innerHTML` کردن دوباره.

**۴. فیلتر هشدار — یک باگ موجود که این کار باید حلش کند.** گزینه‌ی «فقط شورت» در
`index.html` هست و `alertVisible()` هم پشتیبانی‌اش می‌کند، اما اعتبارسنجی موقع بارگذاری
(خط ۱۲۰۱) آن را نمی‌شناسد:

```js
if(['all','buy','watch'].includes(m.filter)) mon.filter=m.filter;   // 'short' جا افتاده
```

تأیید عملی این باگ:

```
saved filter : short
after reload : buy     ← انتخاب کاربر بی‌صدا دور ریخته می‌شود
```

پس کاربر «فقط شورت» را انتخاب می‌کند، صفحه را رفرش می‌کند، و بی‌خبر به «فقط خرید» برمی‌گردد.
هنگام تب‌بندی این یک‌خط باید اصلاح شود، و منطقی است که تب فعال، فیلتر هشدار را هم پیشنهاد دهد.

**۵. مودال مشترک است.** `renderModalInfo()` هم `#mbuy` (لانگ) و هم `#mshort` را پر می‌کند.
با تب‌بندی باید تصمیم بگیریم مودال هم دو بخشی شود یا سمت فعال را اول نشان دهد. پیشنهاد:
هر دو بمانند ولی ترتیبشان با تب عوض شود — اطلاعات کم نشود، فقط اولویت عوض شود.

**۶. تست‌ها باید به‌روز شوند.** `tests/browser.smoke.mjs` بلافاصله بعد از لود، روی
`.short-card` شمارش می‌کند و `#shortEnabled` را `check()` می‌کند. اگر شورت پشت تب پنهان
شود، Playwright روی المان نامرئی شکست می‌خورد. تست باید اول تب شورت را فعال کند.

**۷. نسخه‌ی کش.** طبق قاعده‌ی مستندشده در README، هر انتشاری که HTML/JS/CSS را عوض کند باید
`cryptobin-shell-v4` در `sw.js` را جلو ببرد، وگرنه کاربران قدیمی پوسته‌ی ناسازگار می‌گیرند.

**۸. دسترس‌پذیری.** مخزن به a11y اهمیت داده (`aria-pressed`، `sr-only`، `focus-visible`).
تب‌ها هم باید `role="tablist"`/`role="tab"`/`aria-selected` و پیمایش با کلید جهت‌دار داشته باشند
و تب فعال در `localStorage` (با الگوی `LS_KEYS`) و ترجیحاً در hash آدرس ذخیره شود تا لینک‌دهی کار کند.

## برآورد

تغییر در `index.html` (ساختار تب)، `style.css` (نوار تب + هم‌سطح‌کردن ظاهر شورت)، و بخش
رندر `app.js`. **موتور تحلیل دست نمی‌خورد.** ریسک کم، اثر بصری زیاد.

# ۲) ساختار لاگین

## نتیجه: ممکن است، ولی باید اول درباره‌ی یک واقعیت صریح باشیم

**روی GitHub Pages نمی‌توان لاگین واقعی ساخت.** این محدودیت سلیقه‌ای نیست، ساختاری است:

- Pages فقط فایل ثابت می‌دهد؛ نه سروری هست که رمز را بررسی کند، نه نشستی، نه جای امنی برای راز.
- هر رمزی که در `app.js` بگذاریم، با View Source یا مستقیم باز کردن
  `https://alib11.github.io/Crypto-Market-Analysis/app.js` خوانده می‌شود. هش کردن هم فقط یک
  قدم اضافه می‌کند: مهاجم می‌تواند بررسی را کلاً دور بزند، چون بررسی روی کامپیوتر خودش اجرا می‌شود.
- **خصوصی‌کردن مخزن هم سایت را خصوصی نمی‌کند.** این پرتکرارترین سوءتفاهم است. در مستندات
  GitHub تصریح شده سایت Pages حتی وقتی مخزن خصوصی است، به‌صورت پیش‌فرض عمومی است؛
  «Pages access control» فقط روی **GitHub Enterprise Cloud** در دسترس است.

و یک نکته‌ی مهم درباره‌ی همین سامانه: تمام داده‌های نمایش‌داده‌شده عمومی‌اند (CoinGecko)
و همه‌ی محاسبات در مرورگر خود کاربر انجام می‌شود. یعنی **راز محرمانه‌ای برای محافظت وجود ندارد**؛
آنچه می‌خواهیم کنترل کنیم «چه کسی داشبورد را ببیند» است، نه «چه داده‌ای فاش نشود».

## پس سؤال واقعی این است: لاگین برای چه؟

سه هدف کاملاً متفاوت پشت کلمه‌ی «لاگین» پنهان می‌شود و پاسخ هرکدام فرق می‌کند:

| هدف | آیا روی Pages شدنی است؟ | راه درست |
|---|---|---|
| **الف)** کسی جز من داشبورد را نبیند | ❌ نه به‌صورت معتبر | دامنه‌ی اختصاصی + Cloudflare Access، یا میزبان دیگر |
| **ب)** واچ‌لیست/کارنامه/تنظیماتم بین موبایل و لپ‌تاپ سینک شود | ❌ نیازمند بک‌اند | Worker + KV/D1 یا Supabase |
| **ج)** روی نمایشگر مشترک، داشبورد قفل شود / چند پروفایل جدا داشته باشم | ✅ بله | قفل محلی، با **برچسب صادقانه** |

حدس من این است که نیاز واقعی شما ترکیب **(ج) الان** و **(ب) بعداً** است — چون همه‌ی حالت
برنامه (واچ‌لیست، کارنامه‌ی لانگ، کارنامه‌ی شورت، تنظیمات ریسک، حالت دروازه) امروز در
`localStorage` همان مرورگر است و با پاک‌کردن داده‌ی مرورگر از بین می‌رود. این ضعف در
`REVIEW.md` هم به‌عنوان محدودیت ثبت شده است.

## پیشنهاد: سه پله، با یک «آداپتور احراز هویت»

ایده‌ی کلیدی برای اینکه «به کلیت سامانه ضربه نزند»: یک لایه‌ی نازک واسط بنویسیم که برنامه
فقط با آن حرف بزند، و پیاده‌سازی‌اش قابل تعویض باشد:

```js
// auth.js — قرارداد ثابت، پیاده‌سازی متغیر
Auth.mode()      // 'none' | 'local' | 'remote'
Auth.user()      // null یا {id, name}
Auth.storage()   // آداپتور جای localStorage فعلی
```

اگر `mode==='none'` باشد، رفتار **دقیقاً** مثل امروز است. این تضمین می‌کند نسخه‌ی GitHub Pages
هرگز خراب نشود و همیشه عملیاتی بماند.

**پله ۰ — قفل محلی و پروفایل (بدون زیرساخت، همین حالا):**
صفحه‌ی ورود اختیاری که فقط داشبورد را می‌پوشاند و اجازه‌ی چند پروفایل مجزا می‌دهد
(هر پروفایل، پیشوند کلید جدا در `localStorage`). **باید صریحاً «قفل نمایشی — امنیت واقعی نیست»
برچسب بخورد.** با این کار خواسته‌ی «چند کاربر با تنظیمات جدا» برآورده می‌شود بدون ادعای امنیتی دروغ.

**پله ۱ — احراز هویت واقعی بدون نوشتن حتی یک خط کد بک‌اند:**
دامنه‌ی اختصاصی + **Cloudflare Access** (رایگان تا ۵۰ کاربر). ورود با ایمیل/کد یک‌بارمصرف یا
Google/GitHub، جلوی سایت. این تنها راهی است که هم «واقعی» است و هم به کد فعلی دست نمی‌زند.
دو نکته‌ی مهم:
- آدرس `alib11.github.io/...` همچنان عمومی می‌ماند. برای محافظت واقعی باید میزبانی به
  Cloudflare Pages / Netlify / Vercel منتقل شود (هر سه استقرار مستقیم از همین مخزن Git را پشتیبانی می‌کنند).
- **Service Worker یک تله دارد:** `sw.js` با راهبرد cache-first، پوسته را از کش می‌دهد.
  یعنی کسی که قبلاً سایت را باز کرده، ممکن است رابط را حتی بدون احراز هویت ببیند (داده‌ها
  نمی‌آیند، ولی پوسته می‌آید). اگر پله ۱ را برویم، باید مسیر ناوبری از کش مستثنا شود.

**پله ۲ — حساب کاربری واقعی با سینک:** فقط وقتی معنا دارد که بک‌اند پیشنهاد ۳ ساخته شود.
همان Worker می‌تواند هم احراز هویت بدهد هم سینک. دو پرنده با یک سنگ.

## نکته‌ی سازگاری که نباید فراموش شود

CSP فعلی در `index.html` سخت‌گیرانه است (و این خوب است):

```
connect-src 'self' https://api.coingecko.com https://api.alternative.me
```

هر مبدأ تازه‌ای برای احراز هویت یا بک‌اند **باید** به این فهرست اضافه شود، وگرنه مرورگر
درخواست را بی‌صدا بلاک می‌کند. این جزو چک‌لیست هر پله است.

# ۳) API برای انتقال سیگنال‌ها به سامانه‌ی دیگر

## نتیجه: بله، و به نظر من ارزشمندترین کار از این سه است

اما باید دو معنای متفاوت «API» را جدا کنیم، چون راه‌حلشان کاملاً فرق دارد:

- **الف) خروجی دادن (push):** سیگنال‌ها به تلگرام / ربات معامله‌گر / سامانه‌ی شما بروند.
- **ب) سرویس دادن (serve):** سامانه‌ی دیگری از ما درخواست بگیرد → **این همان چیزی است که
  «کلید API» در آن معنا دارد**، و بدون بک‌اند شدنی نیست.

و یک قاعده‌ی امنیتی که استثنا ندارد: **کلید API داخل مرورگر، کلید عمومی است.** اگر توکن ربات
تلگرام یا کلید صرافی را در `app.js` بگذاریم، هرکسی می‌تواند آن را بردارد. هر طرحی که این
قاعده را نقض کند، از ابتدا رد است.

## خبر خوب: موتور از قبل قابل استفاده در سرور است

این را عملاً بررسی کردم، چون کل امکان‌سنجی پله‌ی ۲ به آن وابسته است:

- در محدوده‌ی `analyze()` تا `setGrade()` (خطوط ۲۱۸–۵۱۹) **هیچ ارجاعی به DOM، `localStorage`
  یا `window` وجود ندارد** — یعنی موتور تحلیل و «بهترین قیمت خرید» توابع خالص‌اند.
- `short-engine.js` مستقیماً در Node بارگذاری می‌شود:

```
$ node -e "require('./short-engine.js'); console.log(Object.keys(globalThis.ShortEngine))"
VERSION, plan, position, advance, restoreRecords, keepRecords
VERSION = short-pullback-v1
```

پس برای ساخت API لازم نیست منطق را از نو بنویسیم — و مهم‌تر، لازم نیست دو نسخه‌ی موازی از
منطق نگه داریم که با هم واگرا شوند. همان کد در مرورگر و در سرور اجرا می‌شود.

## طرح پلکانی

### پله ۰ — قرارداد JSON نسخه‌دار (بدون هیچ زیرساختی، پایه‌ی همه‌چیز)

قبل از هر API، باید یک **شکل داده‌ی رسمی** برای «یک سیگنال با تمام پارامترها» تعریف شود.
خبر خوب اینکه `exportCSV()` و `exportShortCSV()` عملاً ۹۰٪ این فیلدها را از قبل بیرون می‌دهند؛
فقط ساختارمند و نسخه‌دار نیستند. پیشنهاد مشخص:

```jsonc
{
  "schemaVersion": "1.0",
  "generatedAt": "2026-09-16T12:00:00Z",
  "dataAsOf":    "2026-09-16T11:58:30Z",   // تازگی داده — حیاتی برای مصرف ماشینی
  "source": "coingecko",
  "market": { "regime":"riskoff", "gate":"blocked", "fng":22, "breadth":0.18 },
  "signals": [{
    "side":"long",                          // یا "short"
    "strategyVersion":"legacy-long-v1",     // شورت: short-pullback-v1
    "id":"solana", "symbol":"SOL", "name":"Solana",
    "price": 142.15,
    "entry": { "best":138.20, "low":136.1, "high":139.4, "avg":137.8,
               "ladder":[{"step":1,"price":139.4,"weight":40},
                         {"step":2,"price":138.2,"weight":35},
                         {"step":3,"price":136.1,"weight":25}] },
    "exit":  { "stop":129.5, "tp1":151.0, "tp2":158.4 },
    "risk":  { "rr":2.1, "rrNow":1.4, "riskPct":8.9, "wideStop":false },
    "score": { "buyScore":76, "grade":"A", "technical":71, "confidence":63 },
    "gate":  { "state":"open", "reasons":[...], "thresholds":{"score":58,"rrNow":1.0,"rs7":-2.0} },
    "context":{ "rs7":3.2, "pred7d":4.1, "divergence":"RD+" },
    "disclaimer":"تحلیلی/آزمایشی — سیگنال قطعی معامله نیست"
  }]
}
```

چند نکته‌ی عمدی در این طرح:
- `dataAsOf` جداگانه، چون سامانه از قبل منطق دقیقی برای «داده کهنه» دارد (`CACHE_FRESH_MS`)
  و مصرف‌کننده‌ی ماشینی **باید** بتواند سیگنال روی داده‌ی کهنه را رد کند.
- `strategyVersion` داخل هر سیگنال، چون مخزن از قبل هر دو طرف را نسخه‌دار کرده است.
- `disclaimer` داخل payload، چون وقتی سیگنال به ماشین می‌رود، متن پاورقی صفحه همراهش نمی‌رود.

خروجی این پله: یک تابع `buildSignalPayload()` + دکمه‌ی «کپی JSON»/دانلود. **بدون بک‌اند،
بدون هزینه، و کاملاً قابل تست آفلاین** — و همین قرارداد، ورودی هر دو پله‌ی بعدی است.

### پله ۱ — Webhook خروجی از مرورگر

همان رویدادهایی که امروز در `detectEvents()` و `shortCycle()` تشخیص داده می‌شوند، به یک
آدرس دلخواه POST شوند (n8n، Make، یک endpoint خودتان). محدودیت‌های صادقانه:
مرورگر باید باز باشد؛ مقصد باید CORS بدهد؛ آدرس مقصد باید به `connect-src` در CSP اضافه شود؛
و توکن تلگرام نباید در مرورگر باشد (باید از یک relay رد شود).

### پله ۲ — API واقعی با کلید (تنها راه رسیدن به خواسته‌ی اصلی)

موتور به‌صورت headless روی زمان‌بندی اجرا می‌شود و نتیجه را سرو می‌کند. دو شکل ممکن:

**(i) رایگان و ساده — GitHub Actions + Pages:**
یک workflow زمان‌بندی‌شده، موتور را در Node اجرا می‌کند و `signals.json` را در مخزن کامیت
می‌کند؛ Pages همان را سرو می‌کند. یک API فقط-خواندنی و عملاً رایگان.
محدودیت‌های واقعی که باید بدانید: حداقل فاصله‌ی cron **۵ دقیقه** است و در عمل با تأخیر اجرا
می‌شود؛ و در مخزن **عمومی**، workflowهای زمان‌بندی‌شده پس از **۶۰ روز بی‌فعالیتی** بی‌صدا
غیرفعال می‌شوند. ضمناً «کلید API» در این حالت وجود ندارد — خروجی برای همه باز است.

**(ii) API واقعی — Cloudflare Worker + KV/D1 (طرح توصیه‌شده):**

```
GET /v1/signals?side=long&gate=open     → فهرست سیگنال‌های مجاز
GET /v1/signals/{id}                    → یک دارایی با تمام پارامترها
GET /v1/market                          → رژیم، دروازه، ترس و طمع
POST /v1/webhooks                       → ثبت مقصد برای push
Authorization: Bearer <API_KEY>
```

اینجاست که کلید API معنا پیدا می‌کند: کلید سمت سرور به‌صورت هش‌شده ذخیره می‌شود، قابل ابطال
و چرخش است، محدودیت نرخ دارد، و می‌توان مصرف را دید. لایه‌ی رایگان Workers برای این حجم
کافی است، و همین Worker می‌تواند پله ۲ پیشنهاد لاگین (سینک حساب کاربری) را هم سرو کند.

## دو ملاحظه‌ی غیرفنی که واقعاً مهم‌اند

**۱. شرایط استفاده از داده.** پلن رایگان CoinGecko (Demo) حدود ۳۰ درخواست در دقیقه و سقف
ماهانه دارد و **الزام ذکر منبع (attribution)** دارد. بازتوزیع داده‌ی مشتق‌شده از طریق API
خودتان، یعنی ورود به قلمرو شرایط سرویس آنها — پیش از انتشار عمومی API باید بررسی شود.
برای مصرف شخصی/داخلی مسئله‌ای نیست.

**۲. مسئولیت.** وقتی سیگنال به یک سامانه‌ی دیگر (و بالقوه به یک ربات معامله‌گر) منتقل شود،
از «نمایش تحلیلی» فاصله می‌گیرد. تمام هشدارهای `REVIEW.md` همچنان برقرارند: داده sparkline
است نه OHLCV صرافی؛ هیچ بک‌تستی انجام نشده؛ کارمزد، لغزش، فاندینگ و لیکوییدیشن محاسبه
نشده‌اند. پیشنهاد می‌کنم `disclaimer` اجباری در payload بماند و API به‌صورت پیش‌فرض
«فقط تحلیلی» برچسب بخورد.
